# Активация JOKER VPN и подготовка индивидуального доступа

Реализованы серверный учёт срока, одноразовые ключи и экран Android «Подписка».
Добавлена выдача личного VLESS/REALITY-профиля и синхронизация учётных записей Xray.
**Это ещё не система для продажи VPN-доступа:** удаление учётной записи не
гарантирует завершение уже установленных соединений. Исходные ручные профили
не ограничиваются подпиской. До продаж необходимо проверить принудительное
прекращение действующих сессий, отказоустойчивость и восстановление доступа.

## Правила

- Ключ содержит 192 случайных бита, выдаётся локальной командой администратора.
- При первой активации он закрепляется за секретным идентификатором установки.
- Срок увеличивается от `max(серверное время, текущий срок)`.
- Повтор с тем же ключом и идентификатором не добавляет дни снова.
- Другой идентификатор получает отказ. Копия данных приложения переносит тот же
  идентификатор; аппаратной привязки, аккаунтов и ограничения устройств здесь нет.
- В SQLite хранятся SHA-256 ключей активации и идентификаторов установки.
  Личные VPN UUID хранятся отдельно в защищённой базе и являются секретами.
- Неиспользованный ключ по умолчанию истекает через 90 дней. Длительность тарифа
  выбирается при выдаче (1–365 дней), цены и оплата не задаются.
- Потеря данных приложения означает потерю идентификатора. Автоматического
  восстановления пока нет; не выпускайте сервис публично без процедуры восстановления.
- Android показывает дни по серверному ответу на момент проверки. При сетевой
  ошибке не показывает старые дни как актуальные. Дата телефона не используется.

## Проверка локально

```sh
python3 -m unittest discover -s activation -v
python3 activation/server.py --database /tmp/joker-test/ledger.sqlite3 issue --days 30
python3 activation/server.py --database /tmp/joker-test/ledger.sqlite3 serve
```

Сервер слушает только `127.0.0.1:8088`. Административного HTTP API нет.
Ключ из команды `issue` показывается только один раз; не отправляйте его в журналы.
Выданные реальные ключи и база не должны попадать в Git или публичные артефакты.

## Развёртывание сервиса подписок

Нужны доступ администратора к узлу и доверенный HTTPS-сертификат
для домена или IP-адреса. Рабочий Xray занимает TCP/443:
не заменяйте его слушатель. API размещается на отдельном узле/адресе либо отдельном
доверенном HTTPS-порту. Правила хостинга проверяются отдельно перед запуском продаж.

1. Создать системного пользователя `joker-activation` без shell, каталог
   `/opt/joker-activation` с `server.py`, принадлежащим root и недоступным для записи
   пользователю сервиса. Python 3.10+; сторонних зависимостей нет.
2. Установить `joker-activation.service` в systemd и запустить сервис.
3. Поставить перед localhost API TLS reverse proxy: лимит тела 1 КБ, таймаут
   запроса 10 секунд, лимиты соединений и запросов по реальному IP клиента
   (например, 2 запроса/сек, burst 10, не более 5 соединений/IP). Не доверять
   произвольному `X-Forwarded-For`. Не журналировать Authorization и тела запросов.
4. Закрыть внешний доступ к 8088. HTTPS-прокси должен передавать Authorization.
   Не отключать проверку сертификата на Android.
5. Сделать защищённую резервную копию SQLite через SQLite backup API; проверить
   восстановление. База является источником истины, потеря базы теряет подписки.
6. Задать переменную GitHub Actions `JOKER_ACTIVATION_URL`, например адрес
   `https://YOUR-ACTUAL-API-HOST:8444` (без пути, query и завершающего слеша).
   До этого экран честно сообщает, что сервис не подключён, и не принимает ключи.
7. Собрать подписанный APK из этой ветки, установить поверх `com.joker.vpn.app`.
   Проверить активацию, перезапуск приложения, повтор ключа, истечение срока,
   сетевую ошибку, Wi-Fi и Yota. Не использовать Preview для переноса платных прав.

Выдача ключа на сервере:

```sh
sudo -u joker-activation python3 /opt/joker-activation/server.py issue --days 30
```

## Контракт API

`POST /v1/status` с телом `{}` или `POST /v1/redeem` с `{"key":"JOKER-…"}`.
Оба требуют `Authorization: Bearer <64 lowercase hex characters>`.
Клиент генерирует 32 случайных байта и сохраняет их до первого запроса.
Ключ/идентификатор никогда не передаются в URL. Ответы имеют `Cache-Control: no-store`.

Успех: `status` (`inactive`, `active`, `expired`), `remaining_days`, `server_time`,
`expires_at` (Unix seconds). Ошибки: `invalid_key`, `used_key`, `expired_key`,
`invalid_token`, `invalid_request`, `temporarily_unavailable`. Ошибка сети после
запроса активации требует повтора с тем же идентификатором и ключом.

## Синхронизация учётных записей

`server.py` добавляет таблицу `vpn_credentials`: случайный UUIDv4 на подписчика.
Миграция сохраняет старые сроки и ваучеры; повтор и продление сохраняют UUID.
UUID является секретом VPN, поэтому база и резервные копии должны оставаться
закрытыми. Хеши исходных ключей и токенов по-прежнему не раскрываются.
15 ноября пользователь подтвердил установку миграции и успешную синхронизацию
одной активной подписки: `verified: true`, повторная проверка `add: 0`, `remove: 0`.
Описанная ниже выдача профиля требует нового серверного обновления и APK.

`vpn_sync.py` — отдельный локальный административный процесс. HTTP-сервис не
получает доступ к Docker. По умолчанию скрипт только читает базу и Xray и выводит
количества, без UUID, токенов и email. Для чтения нужен уже обновлённый `server.py`.

```sh
sudo python3 /opt/joker-activation/vpn_sync.py
```

Он сравнивает активные подписки с динамическими записями пространства
`joker-sub-<UUID hex>@vpn.invalid`. Остальные учётные записи не изменяет.
Flow берётся из существующей конфигурации; неоднозначный flow останавливает работу.
После перезапуска контейнера динамические записи отсутствуют и добавляются при
следующей успешной синхронизации только для ещё активных подписок.
Нельзя записывать эти динамические UUID в постоянный server.json: это может
восстановить просроченный доступ при перезапуске.

Режим изменения требует `--apply --acknowledge-session-cutoff-pending`. Он
предназначен пока только для интеграционного тестирования. Новый установщик
добавляет `joker-vpn-sync.timer` с интервалом около 30 секунд. Удаление через `rmu`
запрещает новые подключения, но не
гарантирует завершение уже установленных сессий. При недоступности базы или API
программа сообщает об ошибке; старые динамические записи могут остаться в Xray.
Это ещё не надёжное принудительное отключение платного доступа.

План изменений и результат проверяются отдельными чтениями API: успешный exit
code команды `adu` сам по себе не считается подтверждением добавления.
При одновременном продлении/истечении следующий цикл снова сверяет актуальную базу.
CLI сериализует локальные запуски файловой блокировкой; другие администраторы
не должны менять зарезервированное пространство имён параллельно.

## Получение личного профиля

`POST /v1/status` с `{"include_profile":true}` использует тот же Bearer-токен.
Обычный запрос `{}` сохраняет предыдущий контракт. Для активного владельца
ответ содержит `vpn` с `schema: 1`, его UUID и публичными параметрами узла;
для неактивной/истёкшей подписки — `vpn: null`. Токен или UUID в теле запроса
не выбирают чужую учётную запись. Заголовок `Cache-Control: no-store` сохраняется.
Новый путь nginx и доступ HTTP-сервиса к Docker не требуются.

Публичные параметры хранятся в root-owned `/etc/joker-activation/vpn-endpoint.json`.
`configure_endpoint.py` читает Xray локально, вычисляет публичный X25519-ключ,
сохраняет только разрешённые клиентские поля и выводит `ENDPOINT_READY`.
Для этого административного шага используется Python из Certbot venv с cryptography.
HTTP-сервис по-прежнему использует только стандартную библиотеку Python.
Контракт первой версии допускает IPv4, TCP, REALITY, обычный flow или Vision.

Android: «Подписка» → «Добавить профиль VPN». Каждый запрос заново проверяет срок
на сервере. Повтор обновляет один и тот же локальный GUID, не создаёт дубли.
При ошибке публикации индекса восстанавливаются предыдущие данные. Выбор профиля
и переподключение выполняются явно на главном экране; автоматического перезапуска
текущего VPN нет. Секретные поля не попадают в текст ошибок или журнал.

`install_profile_update.sh COMMIT_SHA SERVER_IPV4` запускается root на VPS.
Он скачивает файлы только из указанного полного SHA, запускает серверные тесты,
сохраняет резервные копии кода и SQLite (backup API + integrity check), извлекает
публичные параметры, обновляет backend, проверяет localhost API и включает таймер.
При ошибке восстанавливает прежние файлы приложения. База автоматически не
откатывается, чтобы не потерять параллельно активированные ключи.

15 ноября пользователь показал сохранение «JOKER — Подписка» в новом APK и
успешную синхронизацию одной активной подписки при включённом таймере.
Однако подключение через новый профиль не работает, тогда как старый работает.
Причина ещё не подтверждена; выдача профиля не доказывает успешное подключение.

## Not run — проверки на реальном устройстве и сервере

- Успешное подключение Wi-Fi/Yota через выданный личный профиль.
- Повторное добавление без дублей, закрытие/открытие экрана и проверка сохранённого GUID.
- Принудительное завершение установленных сессий и политика отказа при недоступности API/базы.
- Touch/Enter/Space/D-pad, TalkBack (порядок фокуса и подписи), IME, состояния loading/error/success на устройстве.

## Диагностика личного профиля

`configure_endpoint.py --check --host SERVER_IPV4` — режим только чтения.
Запускать из каталога с установленными `server.py` и `vpn_sync.py`, используя
`/opt/joker-certbot/bin/python` для вычисления публичного X25519-ключа.
Он сравнивает сохранённые параметры API с текущим server.json, а UUID и flow
активных подписчиков — с результатом Xray `inbounduser` (формат Xray 26.7.28).
Результат содержит только фиксированные имена проверок, числа и true/false;
UUID, токены, ключи и параметры узла в вывод не включаются.

- `MISMATCH`: есть несовпадение или отсутствующая/лишняя управляемая запись.
- `NO_ACTIVE_SUBSCRIPTIONS`: срок всех имеющихся подписок истёк либо подписок нет.
- `PARAMETERS_MATCH`: проверенные серверные данные совпадают. Проверка не выполняет
  VPN-подключение и не проверяет настройки сохранённого профиля на телефоне.
- `PROFILE_CHECK_FAILED`: проверить завершение диагностики; ошибка не считается
  подтверждением совпадения данных.

Для режима диагностики проверены отсутствие записи в базу/endpoint, сокрытие
секретов и обнаружение разных UUID/flow при одинаковом числе пользователей.
Not run: запуск диагностики на реальном VPS — доступ к консоли у пользователя.
